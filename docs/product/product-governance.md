# AgenticGame 产品与工程治理

## 1. 三套事实源

- **GitHub 是可执行事实源**：源码、自动化测试、构建脚本、版本标签和发布提交只以 Git 为准。
- **飞书是决策与状态事实源**：产品基线、ADR、开发时间线、质量结论、风险和发布说明维护在 [AgenticGame 知识库](https://ccnhvg4zam5u.feishu.cn/wiki/space/7677277411628567488)。
- **Ardot 是用户界面事实源**：所有用户交互、信息架构和视觉展示以 AgenticGame Ardot 文件中的已验收页面为准。

三者可以互相引用，但不能同时声称自己是同一类事实的最终版本。例如，飞书记录“采用 Replay v2”的理由和状态，Git 保存实际接口与测试，Ardot展示玩家如何查看回放。

## 2. 产品基线

- 游戏优先、代码可选；默认路径不能要求玩家理解 JavaScript、模型参数或运行时术语。
- 复杂度按“快速开战 → AI 指挥官 → 高级工作台”渐进展开。
- 外部 Agent 与内置 BYOK Harness 共享能力模型、沙箱边界和评测口径。
- Bot、装配、规则、地图和比赛包必须版本化、可哈希、可回读。
- 确定性与可解释性优先于表现层便利；任何随机来源都必须显式进入比赛配置。

## 3. 用户界面变更门禁

任何影响用户交互或视觉展示的变更按以下顺序推进：

1. 在飞书记录问题、用户价值和已经确认的约束。
2. 在 Ardot 创建或更新对应页面、状态和关键任务流。
3. 完成布局检查、截图检查和交互走查，记录未解决风险。
4. 代码只实现已验收设计；偏离设计时先回到 Ardot 更新依据。
5. 完成功能、可访问性、响应式和视觉回归验证。
6. 在飞书开发时间线和质量报告中记录结果，在 Git 中提交实现。

没有 Ardot 设计源的用户界面方案不得直接进入实现。纯内部契约、测试和构建修复不受此门禁限制。

## 4. 工程变更门禁

- 新功能和缺陷修复遵循 RED → GREEN → REFACTOR；必须先观察测试因目标行为缺失而失败。
- 核心协议使用版本号和完整 SHA-256；未知持久化字段不得静默忽略。
- v1 兼容迁移使用并行契约和显式适配器，不通过一次性全量重写完成。
- 每个阶段执行“全面检查 → 修复 → 再检查”，至少包括测试、类型检查、构建和 `git diff --check`。
- 不可信 Bot 与模型 Harness 不得共享密钥、文件系统或进程级权限；Node `vm` 不是面向恶意代码的安全边界。

## 5. 飞书同步规则

- `00｜开发时间线`：记录日期、完成事项、验证结果和下一步。
- `03｜UX 与 Ardot 设计`：记录页面、状态、视觉原则和设计验收结论。
- `05｜技术架构与开发环境`：记录长期有效的架构边界与运行环境。
- `06｜开发日志与 ADR`：记录经过权衡的决定，不记录逐行代码细节。
- `07｜测试、平衡与质量`：记录命令、通过数量、失败证据和已知质量风险。
- `08｜版本发布与构建产物`：记录提交哈希、版本、构建产物和已知限制。
- `09｜风险、技术债与待办`：维护仍未关闭的风险；完成项从风险清单移入时间线。

写入后必须回读：确认目标标题只出现一次、内容完整、没有重复时间线记录。Secret、access token、refresh token、API Key 和 Bot 私密凭证不得进入 Git、飞书、Ardot、日志或 Replay。
